# Project factory and country isolation

## Purpose

The v0.7B foundation implements the Google Cloud resource hierarchy, project inventory, project placement, additive IAM, baseline organization-policy guardrails, and project budget controls for the fictional AfyaBridge multi-country health platform.

The package turns the earlier landing-zone design into a statically validated Terraform configuration while preserving strict country and environment boundaries.

## Resource hierarchy

The foundation root creates the following managed hierarchy beneath the Google Cloud organization:

```text
AfyaBridge organization
├── Shared Services
├── Kenya
│   ├── Development
│   ├── Staging
│   └── Production
├── Ghana
│   ├── Development
│   ├── Staging
│   └── Production
└── South Africa
    ├── Development
    ├── Staging
    └── Production
```

Folder deletion protection is enabled. Country and environment folder IDs are generated by Terraform and passed directly to the project factory. Operators do not manually copy folder identifiers into the project inventory.

## Project inventory

Projects are declared in the foundation root as an authoritative map keyed by stable logical names. Each entry defines:

- project ID and display name;
- country and environment scope;
- service purpose;
- owner and cost centre;
- data classification;
- APIs managed by Terraform;
- optional additive IAM bindings;
- optional monthly budget and currency.

Validation requires approved country and environment tokens. Global projects must use the shared environment, and country projects cannot use the shared scope.

## Project factory controls

The reusable project-factory module enforces:

- no automatic default VPC creation;
- protected project deletion policy;
- required ownership, cost, service, country, environment, and classification labels;
- controlled API activation;
- retention of managed APIs when a Terraform resource is removed;
- placement into the generated country or shared-services folder.

Mandatory labels override conflicting optional labels.

## IAM model

Project IAM is managed additively with `google_project_iam_member` resources. This avoids replacing an entire role binding or policy that may be owned by another system.

The module rejects public principals including:

- `allUsers`;
- `allAuthenticatedUsers`.

Committed examples use Google Groups rather than individual user accounts. Production values must use approved identity groups and workload identities.

## Organization-policy baseline

The foundation composes folder-level boolean organization policies for shared services and each country boundary. The initial baseline includes:

- disabling service-account key creation;
- disabling service-account key upload.

These controls reduce long-lived credential risk. Additional location, network, and workload constraints will be introduced only after their compatibility and exception paths are validated.

## Budget controls

Projects may receive a monthly Cloud Billing budget with default thresholds at:

- 50 percent;
- 80 percent;
- 100 percent.

Notification channels are provided as external inputs and are not committed with live identifiers. Budget controls provide visibility and alerting; they do not automatically disable workloads.

## State and authentication boundary

The foundation root is designed to use the protected GCS backend created in v0.7A. Pull-request validation runs without a backend and without Google Cloud credentials.

No service-account key files, billing account identifiers, live folder IDs, notification channels, or production project identifiers are committed.

## Current validation state

The package has passed Terraform formatting, backend-free initialization, and static validation in GitHub Actions. It has not yet been applied to a live Google Cloud organization. Resource creation, effective policy behavior, IAM propagation, billing alerts, and country isolation remain to be verified through a reviewed deployment and evidence capture.
