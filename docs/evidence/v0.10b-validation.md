## Terraform input guardrails added during review

The adversarial reviewer pass found a class of fail-open desired-state risk: a module could have a safe default while its caller was still allowed to override that default to an unsafe value.

The remediation was made in the Terraform contracts themselves rather than only in the observer:

- foundation input validation now requires both `iam.disableServiceAccountKeyCreation` and `iam.disableServiceAccountKeyUpload` to remain enabled;
- workload KMS input validation requires the reviewed 90-day rotation and 30-day scheduled-destruction contract;
- edge backend-log sampling must remain greater than zero, so an enabled log block cannot be rendered operationally silent by setting its sample rate to `0`.

Terraform foundation #325 validated the resulting Terraform across the repository roots.

The review deliberately did **not** freeze every operational tuning value. Cloud Armor rate-limit thresholds remain tunable because the current posture claim is that a throttling action is configured; a zero log sample rate was constrained because it would directly contradict the claim that backend request logging is enabled.

## Cloud Armor preview-first semantics

The final design review found an evidence-semantics issue rather than a Terraform defect. v0.7G intentionally configures the Cloud Armor WAF and per-IP throttling rules in **preview mode by default**, pending representative traffic, false-positive review, and deliberate per-country promotion.

The v0.10B posture rule previously used wording that could be read as if configured `deny(403)` and `throttle` actions were already enforcing traffic. The rule title/messages were corrected so the repository claim is now precise:

- Cloud Armor remains attached to the regional backend;
- WAF deny actions remain configured;
- throttle / `deny(429)` actions remain configured;
- live WAF/rate-limit enforcement is **not** claimed while preview-first rollout remains in effect.

This preserves the intentional v0.7G rollout model without weakening the v0.10B evidence boundary.

## Reviewer findings retained as evidence

### Severity-policy test mismatch

The first v0.10B Security governance execution failed inside the new evaluator negative suite after the real repository posture evaluation itself had passed.

The failed test expected removal of a project ownership label to be merge-blocking. The mapped `GOV-C01` control is Medium under the governed severity policy, where `merge_blocking` is false. The evaluator was correct; the test harness was wrong.

The test was corrected to assert the governed blocking decision explicitly rather than weakening or special-casing the evaluator. The final suite proves both blocking and report-only behavior.

### Executable-rule coverage fail-open risk

The reviewer pass found that an executable rule could retain its ID while silently losing coverage. v0.10B therefore anchors required rule/control bindings, reviewed claim scopes, and all reviewed assertion signatures. Negative tests prove that deleting/remapping a required assertion, weakening a required expected value, shrinking required metadata, or broadening the location-rule claim scope fails closed.

### Source-collector trust hardening

The reviewer pass separated collector/source compromise tests from normalized-fact evaluator tests so both layers are independently exercised. It also excluded generated `.terraform` cache content, added singular/plural public-principal coverage and Cloud Run public-invoker validation, stripped Terraform comments before source matching, and tightened KMS defaults from “some duration exists” to the reviewed 90-day rotation and 30-day scheduled-destruction values.

### Safe-default / unsafe-override risk

The reviewer pass found that safe module defaults were insufficient evidence where callers could still supply unsafe values. Foundation service-account-key policies and workload KMS durations were therefore made non-weakenable through the reviewed input contracts. The same sweep found that edge backend logging could be effectively disabled with a zero sample rate; that input is now constrained above zero and covered by a mutation test.

### Cloud Armor enforcement overclaim risk

The final design pass confirmed that the v0.7G preview-first Cloud Armor rollout was intentional. v0.10B now distinguishes configured WAF/throttle actions from enforcement and leaves live promotion/enforcement validation explicitly pending rather than forcing preview off or overstating current behavior.

## Current boundary

v0.10B currently validates:

- governed executable repository posture coverage;
- normalized desired-state collection from reviewed Terraform contracts;
- fail-closed posture decisions for Critical/High findings;
- report-only handling where governance explicitly defines a non-blocking severity;
- source/collector compromise behavior;
- reviewed Terraform input guardrails for selected security invariants;
- machine-readable and reviewer-readable posture evidence; and
- Terraform drift decision logic with synthetic plans.

It does **not** prove:

- Cloud Asset Inventory collection or queries;
- Security Command Center enablement or findings;
- effective live organization policies or IAM bindings;
- live DNS, network, KMS, Secret Manager, storage, database, logging, or resource-location posture;
- Cloud Armor WAF/rate-limit enforcement while the reviewed rollout remains preview-first;
- a Terraform plan generated against deployed remote state in drift mode;
- a real out-of-band console/manual change and reconciliation; or
- a real cloud finding progressing through remediation and closure.

Those validations remain dependent on the pending live v0.7 Google Cloud deployment path and later v0.10/v0.11 operational testing.
