This evidence records static validation of the v0.7E federated deployment identity foundation.

The reviewed scope includes:

- the reusable GitHub Actions Workload Identity Federation module;
- the federation Terraform environment root;
- the Terraform-generated federation provider lockfile;
- immutable GitHub repository and owner restrictions;
- separate plan and apply OIDC providers;
- separate Terraform plan and apply service accounts;
- fixed deployment-role mappings and impersonation bindings;
- primitive-role rejection;
- the pull-request Terraform plan workflow;
- the approval-gated saved-plan apply workflow;
- the protected-environment and bootstrap runbook;
- the architecture and deployment-role documentation.

Required repository variables are:

- `GCP_FEDERATION_PROJECT_ID`;
- `GCP_WIF_PLAN_PROVIDER`;

A skipped workflow is not positive authentication evidence. It demonstrates only that the bootstrap guard avoids circular failure before federation is configured.

## Validated code-level contracts

Static inspection and validation confirm that the configuration declares:

- one workload identity pool;
- separate OIDC providers for plan and apply;
- immutable numeric repository and owner checks;
- a human-readable repository-name check;
- pull-request plan restriction to the trusted repository and `main` base branch;
- manual plan restriction to the trusted repository and `main` branch;
- apply restriction to `main`, branch ref type, the `production` environment, and allowed events;
- fixed `plan` and `apply` role attributes;
- separate service accounts and impersonation bindings;
- rejection of `roles/owner` and `roles/editor`;
- no service-account key resources;
- destruction protection for the pool, providers, and deployment service accounts;
- pull-request workflow permissions limited to `contents: read` and `id-token: write`;
- same-repository PR gating;
- resource-change counts instead of rendered plan contents;
- manual apply confirmation and exact commit selection;
- saved-plan checksum and provenance metadata;
- protected-environment approval between plan and apply;
- serialized production apply concurrency;
- cleanup of generated credentials and plan files;
- a Terraform-generated lockfile pinning Google provider `7.41.0` with checksums.

## Negative controls represented in code

The implementation does not declare or intentionally support:

- JSON service-account keys;
- repository secrets containing Google Cloud private keys;
- primitive Owner or Editor deployment roles;
- plan-provider impersonation of the apply service account;
- apply from an untrusted branch;
- apply without the protected `production` environment;
- automatic apply from pull requests;
- fork pull-request access to trusted plan federation;
- full Terraform plan publication in PR comments or job summaries;
- automatic cancellation of an in-progress production apply;
- secret payload management through Terraform.

These are code-level properties only. Repository settings, inherited IAM, manually created credentials, workflow modifications, and deployed Google Cloud resources must be inspected separately.

## Evidence limitations

The following remain unverified:

- creation of the workload identity pool and providers;
- actual GitHub OIDC claim values;
- attribute mapping and condition evaluation by Google Cloud;
- positive plan token exchange;
- denial of fork, wrong-repository, wrong-owner, wrong-branch, wrong-event, and missing-environment tokens;
- service-account impersonation;
- effective plan and apply IAM;
- remote-state access and locking;
- GitHub environment reviewers, self-review prevention, and branch restrictions;
- artifact checksum and provenance verification in a real run;
- saved-plan confidentiality within GitHub Actions;
- successful Terraform plan or apply against Google Cloud;
- rollback, recovery, and post-apply drift checks;
- Cloud Audit Logs and GitHub deployment audit correlation.

## Live validation required

Before describing v0.7E as operationally validated:

1. bootstrap the federation root with a separately controlled administrative identity;
2. record the deployed pool, providers, service accounts, and IAM bindings;
3. configure and verify repository variables;
4. configure the `production` environment with reviewers and `main` restriction;
5. run a positive same-repository PR plan;
6. verify a fork PR cannot obtain trusted plan credentials;
7. test wrong repository, owner ID, branch, base branch, event, environment, and deployment-role claims;
8. verify plan credentials cannot impersonate the apply account;
9. execute a non-destructive approved saved-plan apply in a controlled environment;
10. verify checksum and provenance enforcement;
11. inspect GitHub and Google Cloud audit records;
12. run a post-apply no-drift plan;
13. review whether plan and apply identities require further separation by stack and country;
14. remove temporary bootstrap access.

## Result

The v0.7E federation configuration, workflow contracts, and Terraform-generated provider lockfile are suitable for review and controlled bootstrap preparation. They are not evidence of live authentication, least-privilege deployment, protected approval enforcement, or a production-ready delivery path.
