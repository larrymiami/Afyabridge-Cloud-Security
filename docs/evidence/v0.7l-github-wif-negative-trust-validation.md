# v0.7L GitHub Workload Identity Federation Negative Trust Validation — validation evidence

## Scope

This evidence record covers live negative validation of the GitHub Actions → Google Cloud Workload Identity Federation trust boundaries used by the Terraform federation plan and apply identities.

The objective was not to demonstrate another successful deployment. It was to prove that intentionally invalid GitHub execution contexts are rejected at the correct trust boundary, and to distinguish GitHub environment enforcement from Google Workload Identity Federation attribute-condition enforcement.

The validation covers:

- the Terraform plan workflow attempting to assume the dedicated apply identity;
- a non-`main` apply workflow attempting to enter the protected GitHub `production` environment;
- a supplemental non-main/no-environment WIF rejection;
- an isolated `main`-branch apply workflow attempt with the `production` environment deliberately absent; and
- removal of the temporary validation hook after the isolated test completed.

No Terraform resource mutation, state write, service-account key, or long-lived credential was used by these negative tests.

A test-only pull request temporarily changed the Terraform federation plan workflow so that it attempted to authenticate the dedicated apply service account through the apply WIF provider.

```text

```

The Google authentication action reached the apply WIF provider and was rejected with:

```text

```

The workflow then asserted that the authentication outcome was `failure`, and the negative-test job completed successfully.

This proves that a token issued to the Terraform **plan workflow context** cannot cross the apply-provider trust boundary, even when the workflow explicitly requests the real apply provider and the real `terraform-apply` service account.

The test PR was intentionally closed without merge.

## Negative test 3 — isolated production-environment WIF condition

To isolate the Google apply-provider environment condition, a narrowly gated validation mode was added to the real apply workflow through PR `#41`.

The temporary hook was designed so that, when explicitly enabled:

- the normal Terraform plan job was skipped;
- the normal Terraform apply job was skipped;
- no Terraform command executed;
- the job ran from `refs/heads/main`;
- the exact expected commit was asserted;
- the real apply WIF provider was used;
- the real `terraform-apply` service account was requested; and
- the job deliberately had **no GitHub environment**.

PR `#41` merged as:

```text
ae5d754c55c24edf35b2dd580ccb211888dde046
```

The isolated test was dispatched from `main` at exactly that commit.

Workflow run:

```text
31603134297
```

Negative-test job:

```text
94135240477
```

The normal jobs behaved as designed:

```text
plan  -> skipped
apply -> skipped
```

The validation job first proved the expected provenance:

```text
git rev-parse HEAD == ae5d754c55c24edf35b2dd580ccb211888dde046
GITHUB_REF == refs/heads/main
expected_commit == GITHUB_SHA
negative_test_missing_environment == true
```

It then attempted authentication through:

```text
projects/49662756213/locations/global/workloadIdentityPools/github-terraform-apply/providers/github-apply
```

for:

```text
terraform-apply@afyabridge-bootstrap-260808-lm.iam.gserviceaccount.com
```

Google rejected the credential with:

```text
unauthorized_client
The given credential is rejected by the attribute condition.
```

The assertion step confirmed that the auth outcome was `failure` while `GITHUB_REF` remained exactly `refs/heads/main`.

The generated credentials file was then removed by the cleanup step and again by the authentication action's post-job cleanup.

Because repository, workflow path, event, commit and ref were all valid for the apply-provider path while the job deliberately omitted the GitHub `production` environment, this run isolates the environment trust requirement.

**Conclusion:** the apply WIF provider rejects an otherwise valid `main`-branch apply workflow token when the protected `production` environment claim is absent.

## Layered trust result

The live negative tests establish separate enforcement layers:

```text
Plan workflow context
  -> Google apply WIF provider
  -> rejected by provider attribute condition

Non-main apply workflow
  -> GitHub production environment
  -> rejected before runner start

Main apply workflow without production environment
  -> Google apply WIF provider
  -> rejected by provider attribute condition
```

The result is defense in depth rather than reliance on a single branch check:

1. GitHub environment protection prevents non-main branches from entering the production deployment environment.
2. The Google apply WIF provider independently requires the expected apply workflow context and protected environment claim before it will federate the apply identity.
3. The plan workflow cannot exchange its OIDC token for the apply identity.

## Temporary validation-hook cleanup

The isolated environment test required a temporary `workflow_dispatch` input and a dedicated no-environment negative-test job in `.github/workflows/terraform-federation-apply.yml`.

After successful live validation, the hook was removed on the same evidence branch used to publish this record. The workflow content was restored byte-for-byte to the pre-test production form, with blob SHA:

```text
41dbbb0bdc4cadd44160428cc41cf357184afba3
```

The negative-test mechanism is therefore not retained as a standing production bypass or alternate apply path.

## Security conclusions

The negative validation supports the following statements:

- the Terraform plan workflow cannot assume the Terraform apply identity;
- a non-main branch cannot enter the GitHub `production` deployment environment;
- the apply WIF provider rejects an otherwise valid `main` apply workflow token when the `production` environment claim is absent;
- negative tests did not execute Terraform plan/apply operations against the protected backend;
- no service-account JSON key was created;
- no WIF trust condition was weakened to make the tests pass; and
- the temporary environment-isolation hook was removed after validation.

These results complement the successful apply and provider-mutation evidence by showing that the same trust design fails closed under deliberately invalid execution contexts.
