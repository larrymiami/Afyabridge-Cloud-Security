# v0.7H Terraform Bootstrap Live Validation — validation evidence

## Scope

This evidence record covers the first live Google Cloud validation of the AfyaBridge Terraform infrastructure foundation.

The validation applies only to the protected Terraform bootstrap layer in:

```text
infra/terraform/bootstrap
```

It validates:

- live creation and refresh of the Terraform bootstrap control plane;
- remote state protected by Cloud Storage and Cloud KMS;
- service-account impersonation without a downloaded service-account key;
- provider refresh permissions derived from observed API behavior;
- controlled least-privilege mutation testing;
- consolidation from broad temporary discovery roles into custom steady-state roles;
- removal of temporary discovery and bootstrap privileges; and
- a final zero-change Terraform plan after IAM cleanup.

This evidence does **not** claim live validation of the foundation, network, workload, observability, edge, GitHub Workload Identity Federation, protected GitHub environments, or country deployment stacks.

## Authentication boundary

Terraform was executed using Application Default Credentials from an authorized human operator and Google Cloud service-account impersonation.

The effective path was:

```text
Authorized human ADC
        |
        | iam.serviceAccounts.getAccessToken
        v
terraform-deployer
        |
        v
Terraform Google provider
```

No service-account JSON key was created, downloaded, or used.

After bootstrap administration was complete, the operator's temporary project-level IAM grants were removed. A final project IAM query for the human principal returned an empty result while short-lived impersonated credentials remained functional:

```text
RESULT: ADC service-account impersonation succeeded
```

The operator could no longer call `iam.serviceAccounts.getIamPolicy` after the temporary service-account administration grant was removed. This is expected and demonstrates that permission to impersonate the Terraform identity does not imply standing permission to inspect or modify its IAM policy.

## Provider refresh permission discovery

The Terraform Google provider was run under the impersonated `terraform-deployer` identity.

Permissions were derived iteratively from successful provider operations and explicit authorization failures instead of assigning a broad project administration role.

The steady-state bootstrap refresh contract was reduced to:

| Permission | Purpose |
|---|---|
| `resourcemanager.projects.get` | Read bootstrap project metadata required by project-service refresh |
| `serviceusage.services.get` | Read individual Google Cloud service state |
| `serviceusage.services.list` | Enumerate enabled project services |
| `cloudkms.keyRings.get` | Refresh the Terraform state key ring |
| `cloudkms.cryptoKeys.get` | Refresh the Terraform state encryption key |
| `cloudkms.cryptoKeys.getIamPolicy` | Refresh the KMS IAM member managed by Terraform |
| `iam.serviceAccounts.get` | Refresh the Terraform deployment service account |
| `storage.buckets.get` | Refresh state-bucket metadata |
| `storage.buckets.getIamPolicy` | Refresh the state-bucket IAM policy |

During discovery, predefined read-oriented roles were granted only temporarily and with expiration conditions. They included:

```text
roles/browser
roles/serviceusage.serviceUsageViewer
roles/cloudkms.viewer
roles/iam.serviceAccountViewer
roles/iam.securityReviewer
roles/storage.bucketViewer
```

These roles were discovery scaffolding and were removed after the exact steady-state permission contract had been validated.

## Controlled mutation test

A temporary label was selected as a reversible, low-impact mutation of the protected state bucket:

```text
handoff_test = validated
```

The initial Terraform apply was executed without bucket metadata update permission. Terraform reached the Cloud Storage API and failed with:

```text
Permission 'storage.buckets.update' denied
```

This established the negative control:

```text
storage.buckets.get       = sufficient for refresh
storage.buckets.update    = required for bucket metadata mutation
```

A temporary custom role containing only `storage.buckets.update` was then bound specifically to:

```text
projects/_/buckets/afyabridge-tfstate-49662756213
```

Cloud Storage `testIamPermissions` confirmed that the Terraform identity received the exact permission:

```json
{
  "kind": "storage#testIamPermissionsResponse",
  "permissions": [
    "storage.buckets.update"
  ]
}
```

The same Terraform mutation was repeated and succeeded:

```text
Apply complete! Resources: 0 added, 1 changed, 0 destroyed.
```

The temporary label was subsequently removed through Terraform. The revert also completed successfully:

```text
Apply complete! Resources: 0 added, 1 changed, 0 destroyed.
```

A bucket metadata read confirmed that `handoff_test` no longer existed.


The Terraform service account's final project-level IAM inventory therefore contains only:

Terraform backend object access remains separately governed by the state bucket IAM policy.

## Temporary privilege cleanup

Bootstrap and permission discovery used time-bounded IAM bindings for operations including:

- initial state-bucket administration;
- KMS administration;
- service enablement;
- service-account creation;
- custom-role administration;
- provider permission discovery;
- impersonation recovery; and
- service-account IAM administration.

After validation, the temporary bindings were physically removed from the project IAM policy. The cleanup verification query returned an empty result for all IAM conditions with titles beginning `lab1_`.

The temporary `lab1BucketMetadataUpdater` custom role was also removed. No permanent project-level administrative role remains assigned to the human validation identity.

## Final drift validation

After reverting the controlled mutation, installing the final custom roles, removing the broad discovery roles, removing temporary human administration grants, and deleting the temporary test role, Terraform refreshed the complete bootstrap stack successfully.

Final result:

```text
No changes. Your infrastructure matches the configuration.
```

The successful refresh included:

- required Google Cloud project services;
- Cloud Storage project service agent;
- Terraform deployment service account;
- Terraform state KMS key ring;
- Terraform state KMS key;
- KMS IAM member;
- protected Terraform state bucket; and
- state-bucket IAM policy.

This proves that the final reduced permission model is sufficient for the current steady-state bootstrap configuration.

## Security conclusions

The live validation demonstrated that:

1. Terraform can operate through short-lived service-account impersonation without a service-account key.
2. Provider read requirements can be measured rather than approximated with broad predefined roles.
3. Read capability and mutation capability can be separated.
4. `storage.buckets.update` was proven through a denied-before / allowed-after A/B test.
5. Bucket mutation capability can be constrained to the single protected Terraform state bucket.
6. Temporary bootstrap and discovery privileges can be removed without breaking Terraform refresh.
7. The human operator does not retain project-level administration after bootstrap.
8. The final Terraform configuration is drift-free after IAM consolidation.
