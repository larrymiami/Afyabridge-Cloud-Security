# v0.7K GitHub Workload Identity Federation Provider Mutation Validation — validation evidence

## Scope

This evidence record covers live validation of a controlled Google provider mutation performed by the dedicated GitHub Actions Terraform **apply** identity.

The test intentionally changed only the description metadata of the protected Terraform apply service account. The goal was to prove that the production apply workflow can execute a real Google Cloud API mutation while preserving the previously validated plan/apply separation, immutable saved-plan checks, protected state handling, and production approval gate.

The validation covers:

- generation of a one-resource, in-place Terraform plan under the dedicated plan identity;
- immutable saved-plan checksum and provenance verification;
- protected `production` environment approval before apply authentication;
- Google provider read and update permission discovery from live denied operations;
- narrow Stage-0 installation of the measured provider permissions;
- exact service-account-resource scoping for the mutation permission; and
- a final successful Google Cloud provider mutation under `terraform-apply`.

No service-account JSON key was created or used.

## Provider permission discovery

Provider permissions were not predicted or granted through a broad predefined role. They were discovered from live workflow failures.

### Provider pre-update read

The first controlled mutation apply progressed through the protected backend and then failed on:

```text
iam.serviceAccounts.get
```

This demonstrated that the Google provider requires a service-account read before performing the update.

A dedicated Stage-0 custom reader role was created:

```text
projects/afyabridge-bootstrap-260808-lm/roles/afyabridgeTerraformFederationApplyReader
```

Measured permission:

```text
iam.serviceAccounts.get
```

The role is granted to:

```text
serviceAccount:terraform-apply@afyabridge-bootstrap-260808-lm.iam.gserviceaccount.com
```

After this grant, the provider progressed beyond the pre-update read.

### Stale saved-plan safety check

A rerun of only the failed apply job reused the previously generated saved plan. Terraform rejected it with:

```text
Error: Saved plan is stale
```

No permission conclusion was drawn from that attempt. A new workflow run was generated so that the plan reflected the current state revision.

This demonstrated that the pipeline did not bypass Terraform's stale-plan protection during permission discovery.

### Provider update

The next fresh apply reached the actual Google Cloud mutation and failed on:

```text
iam.serviceAccounts.update
```

A second dedicated Stage-0 custom role was created:

```text
projects/afyabridge-bootstrap-260808-lm/roles/afyabridgeTerraformFederationApplyUpdater
```

Measured permission:

```text
iam.serviceAccounts.update
```

The updater role was bound directly on the exact service-account resource:

```text
terraform-apply@afyabridge-bootstrap-260808-lm.iam.gserviceaccount.com
```

for the same apply principal:

```text
serviceAccount:terraform-apply@afyabridge-bootstrap-260808-lm.iam.gserviceaccount.com
```

The mutation permission was therefore not granted project-wide.

## Administrative handoff boundary

Installing the service-account-scoped updater binding required an operator-side IAM policy change. The administration command exposed the required permissions sequentially:

```text
iam.serviceAccounts.getIamPolicy
iam.serviceAccounts.setIamPolicy
```

These permissions were used only for short-lived human administration needed to install the reviewed binding. They are **not** part of the steady-state GitHub apply identity.

The custom provider roles and their externally installed bindings remain Stage-0 administrative handoff artifacts. They are intentionally not delegated to the federation apply stack itself.

In particular, the `terraform-apply` identity was **not** granted:

```text
iam.serviceAccounts.setIamPolicy
resourcemanager.projects.setIamPolicy
```

This prevents the apply identity from changing its own IAM policy or project role assignments and avoids creating a self-escalation path merely to manage its own mutation permission.

## Proven provider contract for this mutation

For this exact service-account metadata update, the live validation demonstrated the following steady-state provider permissions:

```text
iam.serviceAccounts.get
iam.serviceAccounts.update
```

The test did not demonstrate a requirement for broader IAM administration permissions such as:

```text
iam.serviceAccounts.getIamPolicy
iam.serviceAccounts.setIamPolicy
resourcemanager.projects.getIamPolicy
resourcemanager.projects.setIamPolicy
```

Those permissions are therefore not part of the apply identity's provider mutation contract.

The provider contract is intentionally operation-specific. Future Terraform resource types must continue to discover additional permissions from actual denied operations rather than assuming this two-permission set is sufficient for unrelated Google Cloud mutations.

## Security conclusions

The live validation demonstrated that:

1. The plan identity generated a fresh saved plan containing exactly one reviewed in-place metadata mutation.
2. The production apply job executed only after the protected environment gate.
3. The apply job verified saved-plan checksum and provenance before apply authentication.
4. The dedicated apply WIF identity successfully read the protected Terraform backend, acquired state locking, and applied the exact saved plan.
5. Google provider permissions were discovered empirically from live denied operations.
6. `iam.serviceAccounts.get` was sufficient for the provider's pre-update service-account read.
7. `iam.serviceAccounts.update` was the measured mutation permission for the controlled service-account metadata update.
8. The update permission was scoped to the exact `terraform-apply` service-account resource rather than granted project-wide.
9. Operator-only IAM policy administration permissions were kept separate from the GitHub apply identity.
10. The apply identity was not given permission to change its own service-account IAM policy or project IAM policy.
11. Terraform rejected a reused stale saved plan during discovery, preserving the plan/state safety boundary.
12. The final protected workflow completed a real Google Cloud mutation and reported `0 added, 1 changed, 0 destroyed`.

## Remaining Lab 2 boundary

Provider mutation is now proven for the controlled service-account metadata operation.

The remaining validation work is focused on negative trust tests:

- incorrect workflow/ref must not satisfy the intended WIF trust path;
- an incorrect or absent production environment must not satisfy the apply trust path; and
- the plan workflow must not be able to assume the apply identity.

No raw OIDC tokens, Google access tokens, generated credential files, Terraform state, service-account keys, or application-sensitive data are committed as evidence.
