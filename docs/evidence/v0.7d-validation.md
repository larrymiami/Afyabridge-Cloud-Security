# v0.7D validation evidence

## Scope

This evidence records static validation of the v0.7D country-scoped workload deployment foundation.

The validated Terraform scope includes:

- Artifact Registry;
- Secret Manager metadata and access contracts;
- Cloud KMS key rings and symmetric keys;
- Cloud Run services and runtime identities;
- Cloud SQL for PostgreSQL;
- Cloud Storage buckets;
- the composed workload environment root for Kenya, Ghana, and South Africa;
- the Terraform-generated workload provider lockfile.

## Control state

**Implemented and statically validated.**

The Terraform has not been applied to a live Google Cloud organization. This evidence does not prove API availability, IAM effectiveness, encryption state, private connectivity, runtime behavior, backup recovery, data isolation, or deletion safeguards in a deployed environment.

## Validated code-level contracts

Static validation confirms that Terraform can parse, initialize, and validate the composed workload configuration and reusable modules against the locked provider schema.

The configuration declares:

- separate country inventories for Kenya, Ghana, and South Africa;
- immutable Artifact Registry tags by default;
- cleanup policies in dry-run mode by default;
- no public Artifact Registry principals;
- Secret Manager metadata without secret payloads or versions in Terraform;
- regional secret replication, delayed destruction, rotation metadata, and optional CMEK;
- symmetric country KMS keys with rotation and destruction-delay contracts;
- dedicated Cloud Run runtime service accounts;
- digest-pinned Cloud Run images;
- internal Cloud Run ingress and VPC connector egress;
- Secret Manager references rather than plaintext service secrets;
- private-IP-only Cloud SQL instances;
- backup, point-in-time recovery, maintenance, deletion-protection, and CMEK hooks;
- no database users or passwords in Terraform;
- uniform bucket-level access and enforced public-access prevention;
- versioning, soft delete, lifecycle, retention, and CMEK hooks for storage;
- rejection of `allUsers` and `allAuthenticatedUsers` throughout reusable IAM inputs;
- deletion protection and Terraform destruction guards on high-impact resources.

## Negative controls represented in code

The implementation does not declare:

- service-account key resources;
- plaintext secret payloads;
- database passwords or database users;
- public Cloud SQL IPv4;
- public Cloud Run invokers;
- unrestricted Cloud Run ingress;
- mutable tag-only Cloud Run image references;
- public Artifact Registry readers or writers;
- public Cloud Storage principals;
- bucket `force_destroy = true`;
- intentional cross-country resource sharing.

These are code-level properties only. Their runtime absence must be verified after deployment, including inherited IAM and manually created resources.

## Evidence limitations

The following remain unverified:

- project, API, quota, and regional readiness;
- managed-service agent creation and IAM;
- CMEK location compatibility and effective encryption;
- Artifact Registry push, pull, immutability, and cleanup behavior;
- Secret Manager replication, access, rotation notifications, and version recovery;
- KMS encrypt/decrypt behavior and key recovery procedures;
- Cloud Run revision health, invocation, ingress, egress, and secret access;
- Cloud SQL provisioning, private connectivity, backups, restoration, failover, and maintenance;
- Cloud Storage access, retention, lifecycle, version recovery, and soft-delete recovery;
- blocked public access and blocked cross-country access;
- log delivery and secret redaction;
- post-apply drift;
- operational cost, capacity, latency, quotas, and availability.
