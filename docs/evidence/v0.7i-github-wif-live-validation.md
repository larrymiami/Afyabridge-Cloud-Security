# v0.7I GitHub Workload Identity Federation Live Validation — validation evidence

## Scope

This evidence record covers live validation of the GitHub Actions Terraform **plan** identity using Google Cloud Workload Identity Federation.

The validation covers:

- GitHub Actions OIDC authentication;
- Workload Identity Federation token exchange;
- impersonation of the dedicated Terraform plan service account;
- protected Terraform remote-state reads;
- Terraform provider refresh using least-privilege permissions;
- iterative denied-operation permission discovery;
- separation of state-read permissions from infrastructure-refresh permissions;
- service-account IAM-policy reads scoped to the two federation execution service accounts; and
- a final successful zero-change Terraform plan.

This milestone does **not** claim live validation of the dedicated Terraform apply identity or production apply workflow.

## Authentication boundary

The plan workflow authenticated without a downloaded Google Cloud service-account key.

The effective path was:

```text
GitHub Actions
      |
      | GitHub OIDC token
      v
github-terraform-plan WIF provider
      |
      | roles/iam.workloadIdentityUser
      v
terraform-plan service account
      |
      +--> GCS Terraform backend
      |
      `--> Google Terraform provider
```

No long-lived Google Cloud service-account JSON key was created, downloaded, or used.

## State access ownership

The plan identity's state access is intentionally separate from its Google provider refresh access.

A Stage-0 custom role is used for protected-state reads:

```text
projects/afyabridge-bootstrap-260808-lm/roles/afyabridgeTerraformPlanStateReader
```

Final permissions:

```text
storage.objects.list
storage.objects.get
```

The role is bound additively to the protected state bucket for:

```text
serviceAccount:terraform-plan@afyabridge-bootstrap-260808-lm.iam.gserviceaccount.com
```

The additive bucket binding is represented in Terraform by:

```text
google_storage_bucket_iam_member.terraform_plan_state_reader
```

The custom role itself remains a Stage-0 administrative handoff artifact rather than a Terraform-managed resource, preserving the bootstrap ownership boundary.

The plan identity was not granted state-object create, update, delete, or bucket-administration permissions.

## Federation refresh ownership

A separate Stage-0 custom project role provides the provider refresh permissions discovered during live validation:

```text
projects/afyabridge-bootstrap-260808-lm/roles/afyabridgeTerraformFederationPlanReader
```

Final permissions:

```text
resourcemanager.projects.get
iam.workloadIdentityPools.get

```

The role is bound to:

```text
serviceAccount:terraform-plan@afyabridge-bootstrap-260808-lm.iam.gserviceaccount.com
```

Service-account IAM-policy reads are kept separate from the project reader.

A one-permission custom role is used:

```text
projects/afyabridge-bootstrap-260808-lm/roles/afyabridgeTerraformFederationSAIamReader
```

Permission:

```text

```

The plan identity receives that role only on the two federation execution service-account resources:

```text
terraform-plan@afyabridge-bootstrap-260808-lm.iam.gserviceaccount.com
terraform-apply@afyabridge-bootstrap-260808-lm.iam.gserviceaccount.com
```

This avoids project-wide service-account IAM-policy visibility for the plan identity.

## Live denied-operation discovery

Permissions were derived from observed API behavior instead of assigning a broad predefined role.

### Run 31560620304 — backend workspace discovery

GitHub OIDC authentication succeeded, but Terraform backend initialization failed with:

```text
storage.objects.list
```

This established the first protected-state read requirement.

### Run 31562009152 — state-object read

After `storage.objects.list` was granted, the backend configured successfully and then failed reading:

```text
gs://afyabridge-tfstate-49662756213/federation/core/default.tfstate
```

Observed denial:

```text
storage.objects.get
```

The state-reader role was extended with only that permission.

### Run 31562285693 — initial provider refresh

With backend reads working, Terraform entered Google provider refresh and exposed:

```text
resourcemanager.projects.get
iam.workloadIdentityPools.get
iam.serviceAccounts.get
```

These permissions formed the initial federation plan-reader contract.

### Run 31562491754 — propagation confirmation

The project and service-account reads succeeded, while `iam.workloadIdentityPools.get` still returned a denial during the immediate rerun.

A later unchanged run demonstrated that the permission had propagated; no broader permission was added in response to this run.

### Run 31562992763 — pool attestation-rule refresh

After workload identity pool reads succeeded, Terraform progressed to the next pool refresh operation and exposed:

```text
iam.workloadIdentityPools.getAttestationRules
```

The existing federation plan-reader role was extended with only that permission.

### Run 31563251988 — provider and service-account IAM refresh

Terraform reached refresh of all federation resources and exposed two final read requirements:

```text
iam.workloadIdentityPoolProviders.get
iam.serviceAccounts.getIamPolicy
```

`iam.workloadIdentityPoolProviders.get` was added to the project-scoped federation plan-reader role.

`iam.serviceAccounts.getIamPolicy` was deliberately placed in a separate custom role and bound only on the two federation service accounts.

## Temporary privilege handling

Administrative operations required to create or update custom roles and IAM bindings were performed through short-lived human privilege windows.

Temporary privilege included only the administration required for the specific step being performed, such as:

- short-lived custom-role administration;
- temporary exact bucket IAM write permission for the reviewed additive state-reader binding; and
- temporary exact service-account IAM administration for the scoped IAM-policy reader bindings.

These temporary privileges are not part of the GitHub plan identity.

The temporary bucket IAM writer was removed after the reviewed Terraform apply that added the plan state-reader member.

The temporary service-account IAM binder and temporary Role Admin grants were removed after the required permanent bindings were installed.

## Security conclusions

The live validation demonstrated that:

1. GitHub Actions can authenticate to Google Cloud through OIDC and Workload Identity Federation without stored service-account keys.
2. The plan workflow assumes a dedicated `terraform-plan` identity rather than the apply identity.
3. Protected Terraform state reads are separated from provider refresh permissions.
4. State read permissions were discovered empirically and reduced to `storage.objects.list` and `storage.objects.get`.
5. Federation provider refresh permissions were discovered empirically rather than approximated with a broad predefined role.
6. Service-account IAM-policy visibility is scoped to the two exact federation service accounts.
7. The plan identity can refresh all federation Terraform resources without infrastructure mutation permissions.
8. The final GitHub-federated Terraform plan is drift-free.
9. Temporary administrative privilege is not required for steady-state plan execution.
10. The repository now contains an additive Terraform-managed bucket IAM member for the plan state reader without returning to authoritative bucket IAM ownership.
