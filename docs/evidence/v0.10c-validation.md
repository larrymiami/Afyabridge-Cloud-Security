## Governed state machine

The reviewed lifecycle is:

```text
open
  |\
  | +-----------------> risk-accepted
  |                         |
  v                         v
in-remediation <------------+
  |
  v
resolved
  |\
  | +-- verification failed --> in-remediation
  |
  +---- verification passed --> closed
```

`closed` is terminal. A recurrence after closure becomes a new finding so old audit history remains immutable.

## Severity and remediation deadlines

Finding severity is inherited from the active v0.10A control catalogue and cannot be downgraded in the finding record. The existing governance SLA remains authoritative:

| Severity | Maximum remediation time | Merge blocking posture severity |
|---|---:|---:|
| Critical | 24 hours | yes |
| High | 168 hours / 7 days | yes |
| Medium | 720 hours / 30 days | no |
| Low | 2160 hours / 90 days | no |

`remediation_due_at` cannot exceed the severity limit. Open or in-remediation findings past the deadline fail lifecycle validation. Risk acceptance cannot be approved after the original remediation deadline, preventing a late exception from retroactively erasing an SLA breach.

## Source activation boundary

The lifecycle schema recognizes:

- `repository-posture`;
- `manual-review`;
- `terraform-drift`; and
- `security-command-center`.

Only `repository-posture` and `manual-review` are currently active for operational findings.

`terraform-drift` remains inactive until a plan is produced against deployed remote state in a reviewed drift mode. `security-command-center` remains inactive until the live Google Cloud foundation and SCC integration exist. Synthetic tests prove these planned sources cannot be used to fabricate operational findings today.

## Risk acceptance and exception linkage

A risk-accepted finding must use the existing `SEC-EX-YYYY-NNN` registry and satisfy both global and control-specific governance.

The lifecycle validator requires:

- explicit finding-to-exception linkage through `finding_ids`;
- finding owner and exception owner alignment;
- an approved independent exception approver;
- substantive rationale and compensating controls;
- source-specific gate selection;
- control-level permission for exceptions;
- global and control-specific maximum lifetime; and
- proof that the exception was active at each risk-acceptance timestamp.

The reviewed source-to-gate mapping is:

| Finding source | Required exception gate |
|---|---|
| repository-posture | cloud-posture |
| manual-review | cloud-posture |
| security-command-center | cloud-posture |
| terraform-drift | terraform-drift |

### Historical exception finding fixed during review

The first lifecycle design required every linked exception to still be active at the current validation date. That would make a correctly remediated and closed finding become invalid months later when its historical exception naturally expired.

The reviewer pass corrected the semantics:

```text
current risk-accepted finding
    -> exception must be active now

historical acceptance on a later resolved/closed finding
    -> exception must have been active at acceptance time
    -> later natural expiry does not invalidate audit history
```

A dedicated positive test validates the historical-expiry case.

## Resolution attempts and failed verification

Another reviewer finding identified that `resolved -> in-remediation` could not preserve audit evidence if a finding stored only one mutable resolution object. Failed verification would require deleting or overwriting the first remediation evidence.

v0.10C therefore uses immutable `resolution_attempts`:

- every transition to `resolved` creates exactly one attempt;
- a current resolved attempt is `pending` independent verification;
- failed verification records verifier, timestamp, and verification evidence, then requires transition back to `in-remediation`;
- the failed attempt remains in the registry;
- a later transition to `resolved` creates a new attempt; and
- only the terminal attempt may record `passed` verification and close the finding.

The test suite demonstrates both first-attempt closure and a failed-first-attempt / successful-second-attempt path.

## Closure integrity

A closed finding requires:

- final verification status `passed`;
- verifier from the approved governance owners;
- verifier independent from the finding owner;
- verification after the corresponding resolved timestamp;
- terminal `closed` history event;
- `closed_at` equal to that history event;
- terminal history actor equal to the verifier; and
- at least one closure-evidence reference.

The legacy single `resolution` field is rejected to avoid ambiguous evidence once multiple remediation attempts are supported.

## Reviewer findings retained as evidence

The adversarial review found and corrected:

1. **Historical exception expiry bug** — old closed findings would become invalid after an exception expired.
2. **Planned-source overclaim** — SCC and live Terraform drift could otherwise be represented before their integrations existed.
3. **Ungoverned lifecycle actors and exception approvers** — arbitrary actor/approver strings were removed from the trust model.
4. **Source/gate mismatch** — exception gate is now bound to finding source.
5. **Future/retroactive acceptance** — future-created exceptions and acceptance after the remediation SLA are rejected.
6. **Resolution evidence loss** — immutable resolution attempts preserve failed independent-verification evidence across retries.
7. **Closure/history inconsistency** — verifier, verification timestamp, closure timestamp, and terminal lifecycle event are bound together.
8. **Global exception date integrity** — impossible dates, future dates, ID/year drift, and duplicate finding links fail closed.

## Current boundary

v0.10C now proves repository-level governance mechanics for finding ownership, severity-derived deadlines, time-bounded risk acceptance, compensating controls, preserved remediation attempts, independent verification, and evidence-backed closure.

It does **not** prove:

- a live Security Command Center finding;
- a Cloud Asset Inventory finding;
- a Terraform drift finding from deployed remote state;
- a real out-of-band console change;
- a production cloud finding completing remediation and closure; or
- observed remediation SLA performance or posture trends over time.

Those operational claims remain gated on the pending live v0.7 deployment. v0.10D can build reporting and trend metrics on this lifecycle contract without changing these evidence boundaries.
