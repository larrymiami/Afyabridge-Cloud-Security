# v0.7J GitHub Workload Identity Federation Apply Validation — validation evidence

## Scope

This evidence record covers live validation of the GitHub Actions Terraform **apply** identity using Google Cloud Workload Identity Federation and the protected production apply workflow.

The validation covers:

- GitHub Actions OIDC authentication for the dedicated apply identity;
- protected `production` environment approval before apply authentication;
- immutable saved-plan artifact download;
- saved-plan checksum and provenance verification;
- protected Terraform remote-state reads, locking, state persistence, and lock release;
- iterative denied-operation permission discovery for the apply-side GCS backend contract;
- recovery from a stale state lock caused by an intentionally incomplete permission set;
- post-recovery drift validation; and
- a final successful zero-change apply using the exact previously generated saved plan.

This milestone validates the production apply pipeline and apply-side Terraform state access. It does **not** yet claim validation of Google provider mutation permissions for the `terraform-apply` identity because the final saved plan contained no infrastructure changes.

## Live denied-operation discovery

Permissions were discovered from actual GitHub Actions failures instead of assigning a broad predefined role.

### Run 31591319580 — initial apply backend discovery

The plan job completed successfully and the apply job passed:

```text
Check out exact deployment commit
Download saved plan
Verify plan checksum and provenance
Authenticate apply identity
Set up Terraform
```

Backend initialization then failed because the apply identity lacked:

```text
storage.objects.list
```

This established the first apply-side state permission requirement.

### Rerun — state-object read

After `storage.objects.list` was granted, Terraform progressed further into backend initialization and failed reading:

```text
gs://afyabridge-tfstate-49662756213/federation/core/default.tfstate
```

Observed denial:

```text
storage.objects.get
```

The custom apply-state role was extended with only that permission.

### Rerun — state-lock creation

After `storage.objects.get` was granted, backend initialization completed successfully and Terraform entered the exact saved-plan apply.

Terraform attempted to acquire:

```text
gs://afyabridge-tfstate-49662756213/federation/core/default.tflock
```

Observed denial:

```text
storage.objects.create
```

The custom role was extended with only that permission.

### Rerun — state persistence and lock release

After `storage.objects.create` was granted, Terraform successfully acquired the state lock and progressed to state persistence.

The apply then exposed the final observed backend permission requirement:

```text
storage.objects.delete
```

The denial appeared when Terraform attempted to persist the state object and again when it attempted to release:

```text
gs://afyabridge-tfstate-49662756213/federation/core/default.tflock
```

The custom role was extended with only `storage.objects.delete`.

No unobserved state permission was added.

## Stale-lock recovery

Because the run that discovered `storage.objects.delete` could create the lock but could not delete it, Terraform reported a stale lock:

```text
Path: gs://afyabridge-tfstate-49662756213/federation/core/default.tflock
Lock ID: 1786535301063409
```

After confirming the workflow job had completed, the federation backend was initialized through the existing deployer recovery identity and the exact reported lock was removed with:

```text
terraform force-unlock -force 1786535301063409
```

Terraform confirmed:

```text
Terraform state has been successfully unlocked!
```

No lock identifier was guessed and the unlock was not performed while an apply job was still running.

## Separation from the plan identity

The apply-side permissions do not alter the plan identity's read-only state contract.

The plan identity remains limited to:

```text
storage.objects.list
storage.objects.get
```

It was not granted state create, delete, or write permissions during this validation.

The production apply workflow continued to use `terraform-plan` for saved-plan generation and `terraform-apply` only inside the protected apply job.

## Temporary privilege handling

Administrative operations required to create or update the custom apply-state role and install the additive bucket binding were performed through short-lived privilege windows.

Temporary privilege was limited to the specific administration required for the reviewed operation, including:

- short-lived human custom-role administration; and
- temporary exact bucket IAM write permission used to install the additive Terraform-managed apply-state binding.

Temporary administrative privilege is not part of the steady-state GitHub apply identity.

## Security conclusions

The live validation demonstrated that:

1. GitHub Actions can authenticate the dedicated Terraform apply identity through OIDC and Workload Identity Federation without stored service-account keys.
2. Production apply is gated behind the protected GitHub `production` environment.
3. The exact deployment commit is checked out before apply.
4. The immutable saved-plan checksum and provenance are verified before apply authentication.
5. The apply identity is separate from the plan identity.
6. Apply-side protected-state permissions were discovered empirically instead of approximated with a broad predefined role.
7. The apply identity can read Terraform state, create a state lock, persist backend state, and release the lock with the measured four-permission state contract.
8. A stale lock produced during permission discovery was recovered deliberately using the exact Terraform-reported lock ID.
9. A subsequent live plan confirmed the federation state remained drift-free.
10. The final protected workflow successfully applied the exact saved plan and recorded apply evidence.
11. The plan identity remains read-only with respect to protected Terraform state.
12. The repository now contains an additive Terraform-managed bucket IAM member for the apply-state role without returning to authoritative bucket IAM ownership.
